## 1. Project Overview

### Project name

AI-K8s-Twin.

### Problem statement

The project validates a selected Kubernetes application in an isolated/local Kind environment under baseline traffic and controlled failure/resource stress. It collects Kubernetes, k6, and application/resource metrics, evaluates hard requirements deterministically, and can ask Groq for a bounded resource configuration proposal.

### Objective

For one selected microservice at a time:

1. Discover a Kubernetes workload from a supplied repository.
2. Deploy it into the test cluster.
3. Establish a baseline.
4. Run Pod Kill, CPU Stress, Memory Stress, and k6 Traffic Stress.
5. Collect structured metrics.
6. Evaluate hard constraints in backend code.
7. Ask Groq for a bounded candidate configuration.
8. Validate and deploy the candidate.
9. Repeat within configured stopping limits.
10. Preserve a result history for later comparison.

### What the current system does

The current repository contains:

- A CLI that clones a repository and discovers Kubernetes YAML resources.
- A legacy monolithic experiment orchestrator.
- A newer selected-application experiment engine.
- Chaos Mesh YAML templating and execution.
- k6 HTTP/gRPC workload execution paths.
- Kubernetes/kubelet/k6 metric collection.
- Deterministic feature extraction, constraint evaluation, bounds checking, and resource scoring.
- Groq configuration proposal parsing.
- A bounded per-microservice optimization runner.
- Generated per-iteration and final JSON results.
- A separate root `environment-generator` for the older Groq-generated paymentservice example.

### What makes this different from a normal Kubernetes deployment system

A normal deployment system applies a chosen manifest. This project experimentally evaluates a workload, injects controlled failures/resource stress, measures behavior, compares candidate resource configurations, and lets an LLM propose only bounded resource changes. The backend remains authoritative for validation, Kubernetes operations, constraints, and stopping.

## 4. Detailed Data Flow

### 4.1 Input and repository discovery

- **Input:** `--repository-url`, optional `--workload`, available CPU/memory, VUs, duration, optional requirements JSON.
- **Processing:** `optimization_cli.py` calls `workflow.clone_repository()`, `find_yaml_files()`, `parse_yaml_file()`, `analyze_resources()`, and `get_workloads()` from `environment_orchestrator.py`.
- **Output:** Analyzer-shaped workload dictionaries containing kind, name, namespace, file, replicas, selectors, labels, containers, images, ports, and resources.
- **Failure handling:** Missing workload raises `ValueError`; clone and YAML failures propagate as runtime errors.

### 4.2 Workload selection

- `--workload adservice` selects one workload by name.
- If omitted, `optimization_cli.py` uses the first discovered workload.
- The selected experiment CLI in `environment_orchestrator.py` defaults to `adservice` if present, otherwise the first workload.
- Discovery can list all workloads, but active execution should be one workload only.

### 4.3 Candidate extraction

`optimization_policy.configuration_from_application()` extracts the first container's:

- replicas
- CPU request
- CPU limit
- memory request
- memory limit

The candidate does not include image, namespace, container name, ports, probes, services, or other identity fields.

### 4.4 Candidate validation

`optimization_policy.validate_candidate()` validates bounds, quantity parsing, request <= limit, available cluster capacity, and replica range.

`configuration_validator.py` validates analyzer-shaped workload identity and resource structures. `optimization_runner._candidate_application()` deep-copies the selected application and updates only the selected container resources and replicas in a resource override.

### 4.5 Deployment

`environment_orchestrator.deploy_application()` locates the source workload resource, preserves a required ServiceAccount when present, writes a temporary YAML, applies it with kubectl, and waits for rollout. The optimization candidate supplies `resource_override` so the selected Deployment resource values can be changed without asking Groq for arbitrary YAML.

### 4.6 Baseline and experiments

`selected_experiment.run_selected_application()`:

1. Deploys and waits for readiness.
2. Returns a structured failure and skips experiments if deployment fails.
3. Runs baseline k6.
4. Generates and validates Chaos parameters for Pod Kill, CPU Stress, and Memory Stress.
5. Runs Pod Kill.
6. Runs CPU Stress.
7. Runs Memory Stress.
8. Runs Traffic Stress.
9. Collects metrics for each result.
10. Cleans Chaos resources and restores the application.

### 4.7 Feature extraction and constraints

`optimization_policy.extract_features()` reads the baseline and every experiment's metrics for the current result only. It calculates worst-case p95/p99/error/recovery and minimum available replicas. Pod Kill recovery is taken only from `pod_kill_recovery_seconds`.

`optimization_policy.evaluate_constraints()` compares those features with `OptimizationConstraints`. Unknown required values fail; explicitly disabled thresholds are skipped.

### 4.8 Groq proposal

`configuration_optimizer.GroqConfigurationProposalClient` sends the current result, extracted features, constraints, and optimization history to Groq. It accepts only fields in the five-field allowlist and merges them into the current candidate. Unsupported top-level/proposal fields are ignored; invalid JSON or no supported fields raises `OptimizerError`.

### 4.9 Persistence

`optimization_runner.py` writes:

```text
backend/generated/<application>-optimization-iteration-0.json
backend/generated/<application>-optimization-iteration-1.json
...
backend/generated/<application>-optimization-result.json
```

`result_store.py` also provides a UUID-based `backend/results/<run_id>/` store used by the older controller tests/path. The active CLI writes under `backend/generated`.

## 8. Chaos Engineering

### Pod Kill

**Input:** selected application, generated PodChaos YAML, target namespace/`app` label.

**Target selection:** `execute_pod_kill()` lists matching pods before applying Chaos and records the first pod's name and UID.

**Apply:** `apply_chaos_file()` invokes `kubectl apply -f` for the generated PodChaos. The selected engine performs `kubectl apply --dry-run=server` first.

**Timing:** `start_time` is taken immediately before `apply_chaos_file()`. `wait_for_pod_kill_recovery()` polls every three seconds.

**Recovery condition:**

1. The recorded killed pod UID disappears from the selector result.
2. A different pod is Running and has a ready container.
3. The number of ready matching pods is at least the application's expected replica count.

**Metrics:**

- `chaos_apply_seconds`
- `pod_disappearance_seconds`
- `replacement_pod_ready_seconds`
- `total_recovery_seconds`
- `pod_kill_recovery_seconds` (same total timer; used by the optimizer)

Cleanup occurs after the timer stops using `cleanup_chaos(..., ["podchaos"])`.

**Current investigation:** The current values around 32–35 seconds are likely replacement readiness/scheduling and three-second polling overhead after quick pod disappearance. A prior 121.5-second value is consistent with the 120-second recovery timeout plus command/API overhead, but the old artifact lacked phase diagnostics. New runs will preserve the phase timings. Status: **INVESTIGATING**.

### CPU Stress

- Groq generates a bounded parameter, currently typically a percentage such as `50` or `70`.
- `cpu-stress.yaml` uses Chaos Mesh `StressChaos`, targeting the selected namespace and `app` label.
- k6 runs while stress is active.
- Stress duration, cleanup duration, and readiness recovery are stored separately.
- CPU stress does not populate `pod_kill_recovery_seconds`.
- Chaos resources are deleted and readiness is checked afterward.

### Memory Stress

- Groq generates a bounded megabyte value such as `200M`.
- `memory-stress.yaml` uses `StressChaos` memory stress.
- Parameter validation checks the application memory limit.
- k6 runs while stress is active.
- Metrics include memory, OOMKilled, restarts, availability, latency, and errors where sources provide them.
- Stress, cleanup, and readiness timings are separate.

### Traffic Stress / k6

`selected_experiment._run_k6()` uses gRPC k6 contracts for `currencyservice`, `productcatalogservice`, `adservice`, and `shippingservice`; other workloads use the HTTP path. k6 writes JSON output, which is parsed for request count, error rate, p95, p99, and request rate. VUs and duration are configurable. The current code uses VUs/duration; a true target requests-per-second control is not fully implemented.

### Out-of-scope templates

The repository still has network-delay, network-loss, network-partition, and node-failure templates plus legacy execution code. They are not active in `selected_experiment.ACTIVE_EXPERIMENTS`.

## 9. Kubernetes Architecture

- **Docker Desktop/WSL2:** supplies the local container runtime.
- **Kind:** supplies the local Kubernetes cluster.
- **kubectl:** applies manifests, waits for rollouts, queries pods/events/deployments, and cleans Chaos resources.
- **Namespaces:** selected applications use the namespace discovered from their YAML; the paymentservice generator uses `simulation`; older artifacts also use `simulation-resource` or `default` depending on source.
- **Deployment/Pods/Services:** source repository resources are parsed; the selected workload resource is applied. The environment generator renders a `simulation` Namespace, Deployment, and Service.
- **ServiceAccounts/ConfigMaps/Secrets:** ServiceAccount preservation is explicitly handled by `deploy_application`; complete dependency deployment is not universally guaranteed for every discovered application.
- **Chaos Mesh:** consumes the templates in `backend/chaos` and targets the selected workload labels.
- **Prometheus/kubelet:** metrics sources; `kubectl top` may fail when Metrics API is unavailable.
- **k6:** local executable in the active Python/WSL workflow for the selected engine; `backend/k6-runner.yaml` is a separate Kubernetes Pod manifest using namespace `simulation-resource` and ConfigMap `k6-workload`.

A candidate is deep-copied, resource fields are changed in its Deployment resource override, and the existing deployment helper applies/waits for rollout. Kubernetes performs the rollout; Pods are not manually recreated by the LLM.

The LLM must never execute kubectl. The backend creates manifests, validates them, runs server-side dry runs for Chaos, applies resources, waits for rollout, and decides whether to continue.

`environment_orchestrator.collect_result_metrics()` can produce:

- `cpu_max`: maximum collected CPU value; current fallback may equal average for one kubelet sample.
- `memory_avg`: bytes.

- `requests_per_second`: k6-derived request count divided by duration.
- `p95_latency_ms`: k6 p95 milliseconds.

- `pod_restarts`: sum of container restart counts.
- `available_replicas`: Deployment status `availableReplicas`.

- `pod_kill_recovery_seconds`: Pod Kill total recovery timer.
- `chaos_apply_seconds`: PodChaos apply interval.
- `pod_disappearance_seconds`: target disappearance interval.
- `replacement_pod_ready_seconds`: replacement readiness interval.
- `total_recovery_seconds`: same total Pod Kill timer.
- CPU stress duration/cleanup/readiness fields.
- Memory stress duration/cleanup/readiness fields.
- `collection_errors`, `sources`, and `metrics_available`.

### Optimization features

`optimization_policy.extract_features()` aggregates the current result only:

- maximum p95 across baseline/experiments
- maximum p99 across baseline/experiments
- maximum error rate
- maximum `pod_kill_recovery_seconds` only
- minimum available replicas
- any OOMKilled
- observation count

It deliberately ignores generic `recovery_time_seconds` and stress lifecycle durations for the recovery constraint.

### Missing metrics

Missing values remain `null`/UNKNOWN. `selected_experiment._collect()` marks `metrics_available` false when collection errors exist. The optimizer constraint evaluator treats required missing values as UNKNOWN, which fails the evaluation. The current adservice results contain `kubectl top unavailable: error: Metrics API not available`; CPU/memory fallback values came from kubelet stats, while k6 supplied latency/error/request metrics.

### Legacy Prometheus service

`backend/services/prometheus_service.py` is an older polling implementation with hardcoded namespace `simulation-resource` and container `payment`. It is not the authoritative dynamic selected optimization collector.

## 12. LLM / Groq Integration

### Why Groq is used

Groq is used for two proposal/planning roles:

1. The root environment generator asks Groq for an initial paymentservice environment.
2. The optimization layer asks Groq for one next resource configuration based on the current result/history.

### Model

The current configured model is:

```text
openai/gpt-oss-120b
```

### Optimizer input

The optimizer sends:

```json
{
  "current_configuration": {},
  "experiment_result": {},
  "features": {},
  "constraints": {},
  "optimization_history": []
}
```

### Required output

```json
{
  "proposed_configuration": {
    "replicas": 2,
    "cpu_request": "500m",
    "cpu_limit": "1000m",
    "memory_request": "512Mi",
    "memory_limit": "1Gi"
  },
  "reasoning_summary": "Short explanation based only on supplied metrics.",
  "targeted_problem": ["High P95 latency under CPU stress"],
  "expected_effect": ["Reduce CPU contention"]
```

Only the five resource keys are accepted. The backend ignores unsupported fields and validates the merged candidate. The LLM does not output kubectl, YAML, image, ports, probes, namespaces, services, or commands.

Failure behavior includes invalid JSON, missing `proposed_configuration`, no supported fields, quantity/bounds violations, and proposal rejection. The runner stops rather than continuing blindly.

## 13. Optimization Constraints

Current defaults in `OptimizationConstraints`:

```text
max_p95_latency_ms = 200.0
max_p99_latency_ms = None       # skipped
max_error_rate_percent = 1.0
max_recovery_time_seconds = 30.0

```

The 30-second recovery threshold is unchanged. It applies only to `pod_kill_recovery_seconds` in the active optimization policy. It is configurable through the JSON file passed to `--requirements-json`.

A check is PASS, FAIL, UNKNOWN, or SKIPPED. UNKNOWN required metrics make the overall status FAIL.

## 14. Optimization Search Space

Current `ResourceBounds`:

```text
replicas: 1-4
CPU request: 100m-2000m
CPU limit: 200m-4000m
memory request: 128Mi-2Gi
memory limit: 256Mi-4Gi
```

Additional validation:

- CPU request <= CPU limit.
- Memory request <= memory limit.
- Candidate limits must not exceed supplied available CPU/memory.
- Values must parse as supported quantities.
- Only the five resource fields can change.

The bounds are code defaults, not a universal cluster capacity model. A candidate that fails validation is rejected before deployment.

## 15. Objective / Optimal Configuration Definition

Intended definition:

> The lowest-resource configuration that satisfies all defined performance and reliability constraints under the tested scenarios.

The implementation uses a deterministic normalized score:

```text
score = 0.4 * normalized CPU limit
      + 0.4 * normalized memory limit
      + 0.2 * normalized replicas
```

Normalization uses the configured maximum bounds. Lower score is better, but an invalid or constraint-failing configuration is never recorded as a passing best candidate.

The current runner does not exhaustively prove a global optimum. It evaluates Groq's bounded proposal sequence and retains the lowest-scoring passing candidate encountered.

## 16. Stopping Conditions

`OptimizationSettings` defaults:

```text
max_iterations = 4
stagnation_limit = 2
```

The runner stops when:

- The maximum iteration count is reached: `MAX_ITERATIONS`.
- A repeated configuration is encountered: `REPEATED_CONFIGURATION`.
- An experiment result is FAILED: `EXPERIMENT_FAILED`.
- A required metric is UNKNOWN: `REQUIRED_METRICS_UNAVAILABLE`.
- A proposal is invalid or fails: `INVALID_OR_FAILED_PROPOSAL`.
- A passing configuration exists and the next candidate is not lower-scoring: `NO_BETTER_CANDIDATE`.
- A lower-resource passing candidate cannot be continued after a failed candidate: `NO_LOWER_RESOURCE_PASSING_CANDIDATE`.
- Constraint failure count does not improve for the configured stagnation limit: `NO_MEANINGFUL_IMPROVEMENT`.

The backend controls all stopping decisions. Groq does not decide pass/fail or termination.

## 19. Known Issues / Current Investigation

### Pod Kill recovery timing

**STATUS: INVESTIGATING**

The current Pod Kill timer starts immediately before `kubectl apply -f` and stops after the target pod UID disappears, a different replacement pod is Running/Ready, and expected ready replicas are present. Polling is every three seconds. Cleanup runs after the timer stops.

New diagnostics are now emitted:

- `chaos_apply_seconds`
- `pod_disappearance_seconds`
- `replacement_pod_ready_seconds`
- `total_recovery_seconds`
- `pod_kill_recovery_seconds`

The current historical results predate those diagnostic fields. They show target disappearance in roughly 0.57–1.00 seconds and total recovery around 32–35 seconds, so most elapsed time is replacement readiness/scheduling/readiness polling.

A previously reported 121.5-second outlier is not present in the current per-iteration files or current final history; it likely belongs to an older/stale run. The code's 120-second recovery timeout makes a timeout-plus-command overhead the likely explanation, but it cannot be proven without phase diagnostics from that run.

### Metrics API

**STATUS: OPEN**

`kubectl top` reports `Metrics API not available` in current result artifacts. Kubelet stats and k6 provide partial fallback data, but `metrics_available` is false and resource metrics may be incomplete.

### Legacy path divergence

**STATUS: OPEN**

The repository retains a large legacy `process_application()` path that assumes Pod Kill + five network/stress environments + Node Failure and can process every workload. The active selected optimizer does not use that sequence by default, but future agents must avoid accidentally routing new optimization work through the legacy path.

### k6 target rate

**STATUS: OPEN**

The active k6 path is configured primarily by VUs and duration. A true target requests-per-second control is not fully implemented even though request rate is measured afterward.
